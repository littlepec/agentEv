# Hand-Crafted Template Counts for Knowledge-Base Question Generation

## Direct Answer and Scope

The reported system used **two distinct hand-crafted template totals**, because the manual template-building effort was tied to each knowledge base rather than to a single universal template set. For the Freebase evaluation, the authors hand-crafted **106 templates** for 500 randomly selected triples ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). For the in-house power tool domain knowledge base, the authors hand-crafted **163 templates** for 67 predicates ([document_2.txt](document_2.txt)). Therefore, if the question refers to the Freebase experiment, the answer is **106**; if it refers to the in-house power tool domain, the answer is **163**.

This distinction matters because the system’s template construction is predicate-centric. Each template is associated with a predicate in the knowledge base, and the number of templates therefore scales with predicate coverage rather than with the total number of triples or entities ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). The two reported counts are not contradictory; they reflect two different knowledge bases with different predicate sets and different evaluation goals ([document_2.txt](document_2.txt)).

## Background: Why Templates Are the Central Manual Component

The system contains several sub-modules: question template construction, seed question generation, question expansion, and selection ([document_1.txt](document_1.txt)). Given an input knowledge base, a small set of question templates is first constructed so that each template is associated with a predicate ([document_1.txt](document_1.txt)). A seed question set is then generated by applying the templates to the input knowledge base ([document_1.txt](document_1.txt)). After that, additional questions are retrieved iteratively from a search engine by using already-obtained questions as search queries ([document_1.txt](document_1.txt)).

The paper states that the **only human labor** in the work is question template construction ([document_1.txt](document_1.txt)). This means the template counts are not a minor implementation detail; they are the primary measure of manual effort in the reported system. The template design also explains why the system can operate with a relatively small number of templates: multiple entities in the knowledge base share the same predicates, and the iterative question expansion can produce many questions even from a relatively small seed set ([document_1.txt](document_1.txt)). The authors also note that the system can easily generate updated questions because the web is self-updating consistently ([document_1.txt](document_1.txt)).

Templates consist of a transcription of the predicate in the knowledge base and placeholders for the subject and object ([document_1.txt](document_1.txt)). For example, the predicate “performsActivity” can be transcribed into the template “how to use #X#” ([document_1.txt](document_1.txt)). Applying that template to the triple ⟨jigsaw, performsActivity, CurveCut⟩ produces the seed question “how to use jigsaw” ([document_1.txt](document_1.txt)). This example illustrates the logic of the entire template-count question: one predicate can yield a reusable template that applies to many entities.

## Freebase Evaluation: 106 Hand-Crafted Templates

In the Freebase evaluation, the work used 500 randomly selected triples ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). The paper reports **106 hand-crafted templates** for those 500 Freebase triples ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). The reason the template count is not 500 is that the triples share only **53 distinct predicates** ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). On average, the authors made **2 templates for each predicate** ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)).

Applying the templates to the triples generated **991 seed questions** ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). The experiment also retrieved **1,529 more questions from Google** ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). This design ties template creation to predicates and keeps the template set compact relative to the triple set ([document_2.txt](document_2.txt)). In other words, 106 templates were sufficient to cover 500 triples because the triples collapsed into 53 predicate types, and each predicate received roughly two templates.

The Freebase evaluation also included a fluency assessment. The authors trained a 4-gram language model on Gigaword with Kneser-Ney smoothing, used the averaged language model score as an index, and selected the top 500 questions to compare with prior results ([document_1.txt](document_1.txt)). Three native English speakers evaluated fluency and naturalness, including whether people would ask the questions in reality, using a 4-point scheme where 4 is the best ([document_1.txt](document_1.txt)). The abstract reports that questions generated by the system were judged to be more fluent than those of the compared system by human graders on the 500 randomly selected Freebase triples ([document_1.txt](document_1.txt)). The introduction similarly reports that questions generated by the system were significantly better on grammaticality and naturalness when evaluated by three human graders ([document_1.txt](document_1.txt)).

## In-House Power Tool Domain: 163 Hand-Crafted Templates

For the in-house power tool domain knowledge base, the paper reports **67 predicates** ([document_2.txt](document_2.txt)). For those 67 predicates, the authors hand-craft **163 templates** ([document_2.txt](document_2.txt)). That count differs from the Freebase template count because the domain-specific knowledge base has its own predicate set and required its own template set ([document_2.txt](document_2.txt)).

The Freebase and power tool counts together provide the reported template-construction figures for the system ([document_2.txt](document_2.txt)). These figures show that manual template-building effort scales with predicate coverage in each evaluation ([document_2.txt](document_2.txt)). For the power tool domain, 163 templates for 67 predicates implies an average of approximately **2.43 templates per predicate**, which is close to the Freebase average of 2 templates per predicate ([document_2.txt](document_2.txt)). That approximate average is a derived figure based on the reported 163 templates and 67 predicates, not a separately stated average in the source ([document_2.txt](document_2.txt)).

The power tool domain also produced a much larger question set. The authors generated **12,228 seed questions**, from which **20,000 more questions** were expanded with Google ([document_1.txt](document_1.txt)). The expanded questions were generally grammatical and relevant to the power tool domain ([document_1.txt](document_1.txt)). Most were informative and corresponded to a specific answer, except for an example question such as “do I need a hammer drill,” which lacks context information ([document_1.txt](document_1.txt)). The system also generated complex questions such as “how to cut a groove in wood without a router” ([document_1.txt](document_1.txt)). Examples of expanded questions include “how to change circular saw blade,” “how to measure lawn mower cutting height,” “how to sharpen drill bits on bench grinder,” “how does an oscillating multi tool work,” “what type of sander to use on deck,” and “can I use acrylic paint on wood” ([document_1.txt](document_1.txt)).

## Comparative Interpretation: What the Template Counts Mean

A concrete assessment based on the reported figures is that the **106** and **163** template counts should be understood as predicate-denominated counts, not as evidence that the authors had to write a unique template for every triple. In Freebase, 500 triples reduced to 53 distinct predicates, and 106 templates covered them at roughly two templates per predicate ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). In the power tool domain, 67 predicates required 163 templates ([document_2.txt](document_2.txt)). Thus, the manual effort is bounded by predicate coverage, not by entity count or triple count.

This is the most important interpretive point. If the question asks “How many hand-crafted templates did they have to make?” the most accurate reply is: **they had to make 106 hand-crafted templates for the Freebase evaluation and 163 hand-crafted templates for the in-house power tool domain knowledge base**. There is no single universal template count because the system constructs templates for the predicates present in each knowledge base ([document_2.txt](document_2.txt)). The reported counts also demonstrate that the system does not require a large number of templates, because iterative question expansion can produce many questions even with a relatively small number of seed questions, and because multiple entities share the same predicates ([document_1.txt](document_1.txt)).

The contrast with prior work strengthens this interpretation. Previous work relied on massive human-labeled data, and one reported neural machine translation approach trained on **10,000 ⟨triple, question⟩ pairs** in which the question part was human generated ([document_1.txt](document_1.txt)). That approach required a large amount of human effort, and the grammaticality and naturalness of generated questions could not be guaranteed ([document_1.txt](document_1.txt)). By comparison, the template-based system’s manual component is limited to 106 templates for Freebase and 163 templates for the power tool domain, with the rest of the question volume coming from seed generation and web-based expansion ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). In my assessment, this is a meaningful reduction in manual annotation effort, although it does not eliminate human labor entirely.

## Evaluation Context and Quality Claims

The system was evaluated by human graders on 500 randomly selected triples from Freebase ([document_1.txt](document_1.txt)). The questions generated by the system were judged to be significantly better than the compared system on grammaticality and naturalness ([document_1.txt](document_1.txt)). The abstract also states that the system’s questions were judged to be more fluent than those of the compared system by human graders ([document_1.txt](document_1.txt)). These quality claims matter for the template-count question because they suggest that a relatively compact template set, combined with web expansion and selection, can produce fluent and natural questions.

The selection process used a 4-gram language model trained on Gigaword with Kneser-Ney smoothing, and the top 500 questions were selected for comparison ([document_1.txt](document_1.txt)). Three native English speakers evaluated fluency and naturalness on a 4-point scheme, where 4 is the best ([document_1.txt](document_1.txt)). For the power tool domain, the expanded questions were mostly grammatical and relevant, and most corresponded to a specific answer ([document_1.txt](document_1.txt)). The domain relevance evaluation used Wikimedia dumps ([document_1.txt](document_1.txt)). These evaluation details support the conclusion that the reported template counts were not merely a cost-saving shortcut; they were part of a system that produced questions judged to be fluent and domain-relevant.

## Limitations and Future Work

The system generates questions without answers, and automatic answer mining is left as future work ([document_1.txt](document_1.txt)). The template construction remains the only human labor reported ([document_1.txt](document_1.txt)). Therefore, any new predicate or new domain still requires manual template creation, even though the number of templates is much smaller than the number of possible triples or questions ([document_2.txt](document_2.txt)). The Freebase count of 106 templates and the power tool count of 163 templates are thus both a measure of efficiency and a reminder that the approach depends on manual predicate-level design.

A further limitation is that the template counts are tied to the specific knowledge bases used in the experiments. The Freebase evaluation used 53 distinct predicates and 106 templates, while the power tool domain used 67 predicates and 163 templates ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). These figures should not be generalized to all possible knowledge bases without accounting for the number and complexity of predicates in those bases. The reported evidence does, however, show that the template-building effort scales with predicate coverage in each evaluation ([document_2.txt](document_2.txt)).

## Conclusion

The hand-crafted template counts reported in the provided documents are **106 templates for the Freebase evaluation** and **163 templates for the in-house power tool domain knowledge base** ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). The Freebase count covered 500 randomly selected triples that shared only 53 distinct predicates, yielding an average of two templates per predicate ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). The power tool count covered 67 predicates ([document_2.txt](document_2.txt)). The system’s design ties template creation to predicates, keeps the template set compact relative to the triple set, and relies on seed question generation and iterative web expansion to produce a much larger question volume ([document_1.txt](document_1.txt); [document_2.txt](document_2.txt)). The direct answer to the query is therefore not a single number but a pair of reported counts: **106 for Freebase and 163 for the power tool domain**.
